# djames-py

A pure-Python reference implementation of **James** and **D-James**, the
ultra-short multivariate signature schemes of

> Jacques Patarin and Alexandre Roullet,
> *D-James: Ultra Short Multivariate Signatures*,
> IACR Cryptology ePrint Archive **2026/1650**, <https://eprint.iacr.org/2026/1650>
> (local copy: [`../ref/2026-1650.pdf`](../ref/README.md))

> [!WARNING]
> **Do not use this for anything real.** It is not constant-time, has had no
> security review, and exists to make the paper concrete and to produce test
> vectors. The scheme itself is also new: the paper's own authors write that
> they "do not recommend deploying these signatures in security-critical
> applications until they have undergone further scrutiny and extensive
> analysis by the cryptographic community."

Written from the paper. The authors' SageMath proof-of-concept is archived in
[`../ref/`](../ref/README.md) but no code was taken from it; where the two
disagree, this follows the paper (see [Reading the
paper](#reading-the-paper)).

## Status

The algebra is complete and internally consistent — both schemes, all five base
fields, all twenty parameter sets — and the public key is checked to reproduce
the secret central map coefficient-for-coefficient, not merely to accept the
signatures we produce (see [Testing](#testing)). Signature encoding is exact
and canonical.

What is **not** settled is literal conformance to the paper. Two of its
statements are self-contradictory and only the authors can resolve them: the
**Dragon index range** and the **`q = 4` central monomials**. In both cases we
picked the reading the rest of the paper supports, and both are recorded below.
A third table entry (`m` for `q = 4` at 256-bit) is corrected rather than
instantiated literally. The known-answer vectors are regression vectors
generated by this code, not independent conformance vectors.

## Quick start

No dependencies — Python 3.8+ and the standard library.

```python
from djames import get_params, keygen, sign, verify

P = get_params("d-james-128-q2")          # the paper's headline set
pk, sk = keygen(P, b"\x01" * 32)          # deterministic in the seed
sig = sign(P, sk, b"hello")               # 24 bytes = 189 bits
assert verify(P, pk, b"hello", sig)
```

```console
$ python3 -m unittest discover -s tests -v                  # correctness
$ DJAMES_FULL_KAT=1 python3 -m unittest discover -s tests   # + every KAT file
$ python3 tools/gen_kat.py toy                              # regenerate vectors
```

Or from the repository root, `make test`, `make test-full`, `make kat`;
`make clean` removes Python and Sage scratch (`make help` lists them all).

## What is implemented

Both schemes, over all five base fields, at every parameter set in Tables 3–6:

* **James** = HFE⁻_IP. Public key is `m` quadratic forms in the `n` signature
  variables; verification checks `P(a) = Hash(msg)`.
* **D-James** = the same plus **Dragon** terms — bilinear couplings `a_i b_j`
  between the signature variables and the hash variables. The public system is
  homogeneous and verification checks `P(a, b) = 0`.

The Dragon terms are the whole trick. Fixing the message hash `y` turns each
`L_k(y)` into a *constant* of `K`, so the central map collapses to a univariate
polynomial of degree `D = q^d + 1` and inverting it costs no more than plain
HFE — while the number of published equations `m` is decoupled from the hash
length `n_y`. That is what lets the signature be shorter than `2λ` bits.

The central map, as implemented (`djames/scheme.py`):

```
H(X, y) = Σ_{(i,j) ∈ monomials} λ_ij X^(q^i + q^j)     HFE core
        + Σ_{k ≤ d}  L_k(y) X^(q^k)                    Dragon   (D-James only)
        + Σ_{k < d}  Σ_j M[k][j] z_j X^(q^k)           IP, bilinear
        + Σ_{i ≤ j}  G[i][j] z_i z_j                   IP, quadratic
```

with `z = M_Z x ∈ F_q^r`, `L_k(y) = Σ_j Λ[k][j] y_j ∈ K`, `x = a S`, and the
public key `Π ∘ T ∘ H ∘ S` truncated to its first `m = n − a` equations (the
minus modifier).

## Design

**SHAKE256 is the only primitive.** Key expansion, message hashing, the James
minus-padding, and the randomness inside equal-degree splitting all come from
`hashlib.shake_256`, each under its own domain-separation label
(`djames/symmetric.py`). Consequently `keygen(P, seed)` and `sign(P, sk, msg)`
are bit-deterministic functions of their inputs — which is what makes the test
vectors reproducible. A secret key *is* its 32-byte seed.

**Packed-integer field arithmetic.** A list-of-ints encoding of `K` is hopeless
at `n = 390` with `n_y = 512`, so every vector over `F_q` lives inside a Python
big integer and the bulk arithmetic is `int` operations running at C speed
(`djames/ff.py`). Three backends:

| q | representation | addition | product |
|---|---|---|---|
| `2` | one coefficient per bit | `^` | carry-less multiply via 16-bit bit-spreading |
| `2^k` | `k` bit-planes | plane-wise `^` | `k²` carry-less products |
| `p` odd | one coefficient per `B`-bit lane | `+`, lanes stay independent | **a single `int` multiply** |

The odd-`p` case is the nice one: lane `k` of `a*b` accumulates
`Σ_{i+j=k} a_i b_j ≤ n(q−1)²`, comfortably below the lane width, so one
big-integer multiplication *is* the whole schoolbook polynomial product and only
the lane reduction costs per-coefficient work.

Two more places where the structure pays:

* **Rabin irreducibility.** On `F_q[t]/(f)` the map `h ↦ h^q` is `F_q`-linear
  (the coefficients lie in `F_q` and are fixed by it), so each of the `n`
  iterations is one linear combination rather than a modular exponentiation.
  Finding all 26 field polynomials takes under 70 s total.
* **Public-key assembly.** Every term of `H` is a product of two `F_q`-linear
  forms, hence contributes a rank-one outer product `u ⊗ v` over `K`. Folding
  the IP families over their inner index first cuts the term count from
  `d·r + r(r+1)/2` to `d + r`, and the output projection is applied once per
  monomial rather than once per term.

## Reading the paper

The paper specifies a design, not a wire format. These are the choices this
implementation makes; all are documented at their definitions.

| Question | Paper | Here |
|---|---|---|
| Hash to `F_q^{n_y}` | unspecified | SHAKE256, domain-separated, rejection-sampled for non-power-of-two `q` |
| Field polynomial for `K` | unspecified | canonical: least `f = t^n + Σ c_i t^i` by the integer with base-`q` digits `(c_0,…,c_{n-1})` that is irreducible; cached in `fieldpoly.json`, pinned in every vector |
| Salt transmission | footnote 5: omit it, verifier searches | omitted; verifier walks `salt = 0,1,2,…` |
| Salt bound | unspecified | `MAX_SALT = 256`. Security-relevant, not just an engineering limit — a forger may aim at any of those hash values, conceding `log₂ 256 = 8` bits. Treating salts as independent and taking the paper's expected trial counts (1.582 in characteristic 2, 3.07 otherwise — its footnote 3), per-salt failure is 0.368 and 0.674, so 256 salts fail with probability ≈ 2⁻³⁶⁹ and ≈ 2⁻¹⁴⁶; the odd-characteristic figure is the binding one |
| James minus-padding | "uniformly random elements", replacing the salt | derived from a per-key PRF key, so signing is deterministic |
| Dragon index range | **contradictory.** The text names the maps `L_0, …, L_{d-1}` (so `k < d`), and §4.2's MinRank argument wants only the first `d` rows of `H̃` nonzero — but the displayed sum runs over `q^i ≤ D = q^d + 1`, which includes `i = d` | `k ≤ d`, following the displayed sum and the authors' notebook. **Unresolved in the paper; worth confirming with the authors.** Note `H̃`'s `λ` block already occupies row `d` (via `q^d + q^0 ≤ D`), so the "first `d` rows" claim is loose either way |
| IP bilinear index | §2.3: "degree with respect to `X` less than `q^d`" | `k < d`. The authors' notebook uses `k ≤ d` |
| Linear / constant terms in `H` | absent from `H(X,Y)`; footnote 4 says the public system is homogeneous | absent, so the system is homogeneous. The notebook adds linear terms |
| Zero signature | footnote 4: must be excluded | `verify` rejects `a = 0`; the signer skips the root `X = 0` |
| Leading coefficient | "random" | drawn nonzero, so `deg H = D` exactly |
| Byte encoding | unspecified | **signatures**: the whole vector as one base-`q` integer — exactly `⌈n log₂q / 8⌉` bytes, and canonical, so each signature has exactly one accepted byte string. **public keys**: group packing (a single base conversion over millions of digits would be quadratic), ≥ 99% of the information-theoretic size, with every group validated on decode (`djames/codec.py`) |
| Zero signature under James | specified only for homogeneous D-James | rejected for James too. A deliberate deviation: `P(0) = 0`, so `a = 0` could only ever verify for a message whose hash is all-zero — finding one costs `q^m`. Rejecting it is a strengthening with negligible completeness cost |

### Discrepancies in the paper's tables

Found while transcribing the parameters. None affect the design; all are
resolved in favour of the paper's own defining relations.

1. **Table 4, `q = 4`** lists `m = 180` with `n = 223`, `a = 53`, and
   **Table 8 repeats the same triple** — so it is not an isolated typo. The
   table header defines `m = n − a`, which gives 170, and every other row of
   every table satisfies that exactly, so we take `m = 170`. But this resolves
   the defining relation rather than instantiating the literal row: only the
   authors can say whether `m` or `a` is the wrong entry.
2. **All four `q = 4` rows — Tables 3, 4, 5 *and* 6** — list the central
   monomials as `X³, X¹⁷`. Over `F_4` there is no `X³ = X^(q^i + q^j)`;
   `X¹⁷ = X^(4²+4⁰)` is fine. Every other row of every table uses
   `X² = X^(q⁰+q⁰)` as its low monomial (`F_2` alone uses `X³`, because `X²` is
   `F_2`-linear there and so useless as a quadratic term). We read it as `X²`.
   This is a *correction* to the paper, not literal conformance.
3. **The `|PK|` column reproduces for James but not for D-James.** Reading the
   paper's `M`/`k` as binary prefixes, our serialized public keys match
   Tables 5–6 to within 1–4% on **nine of ten** James rows — so the encoding
   and the coefficient count agree. Two things stand out:

   | set | measured | paper `|PK|` | paper / measured |
   |---|---:|---:|---:|
   | `james-128-q2` | 1,285,952 B | 2.45 M | **2.00** |
   | `james-128-q4` | 357,600 B | 346 k | 0.99 |
   | `james-128-q5` | 282,879 B | 274 k | 0.99 |
   | `james-128-q13` | 136,045 B | 130.9 k | 0.99 |
   | `james-128-q23` | 100,356 B | 95.8 k | 0.98 |
   | `james-256-q2` | 10,709,184 B | 10.2 M | 1.00 |
   | `james-256-q4` | 3,065,280 B | 2.92 M | 1.00 |
   | `james-256-q5` | 2,417,283 B | 2.30 M | 1.00 |
   | `james-256-q13` | 1,195,727 B | 1.13 M | 0.99 |
   | `james-256-q23` | 913,824 B | 857 k | 0.96 |
   | `d-james-128-q2` | 1,343,365 B | 1.04 M | 0.81 |
   | `d-james-128-q4` | 399,105 B | 163 k | **0.42** |
   | `d-james-128-q5` | 315,765 B | 91.4 k | **0.30** |
   | `d-james-128-q13` | 218,218 B | 225 k | 1.06 |
   | `d-james-128-q23` | 211,788 B | 240 k | 1.16 |
   | `d-james-256-q2` | 11,174,963 B | 8.82 M | 0.83 |
   | `d-james-256-q4` | 3,487,720 B | 3.02 M | 0.91 |
   | `d-james-256-q5` | 2,969,307 B | 2.70 M | 0.95 |
   | `d-james-256-q13` | 2,107,885 B | 2.28 M | 1.13 |
   | `d-james-256-q23` | 2,008,160 B | 2.36 M | 1.23 |

   * **`james-128-q2` is out by a factor of exactly 2.00**, against nine
     sibling rows that land within a few percent. It reads like a doubled
     value rather than a different accounting.
   * **The D-James rows scatter from 0.30 to 1.23** with no consistent
     relationship. The `q = 4` and `q = 5` rows of Table 3 are the extreme
     cases and look as though the `n · n_y` Dragon block — which is the larger
     half of a D-James key — went uncounted.

   Since the same encoder produces both columns, and it reproduces the James
   table almost exactly, the arithmetic here is worth a second look. Note this
   affects only the reported key sizes; signature sizes all check out.
4. **Signature sizes round differently for `q = 23`**: the paper reports 334 and
   737 bits where `⌈n·log₂ 23⌉` is 335 and 738. Every other entry in the
   `|sig_fast|` column matches our computed `sig_bits` exactly — which is a
   useful confirmation that the rest of the parameter transcription is right.

We do not implement `|sig_short|`, the truncated variant: recovering the
dropped symbols at verification time means running a hybrid Gröbner solve,
which is out of scope for a reference implementation.

## Performance

Pure Python on one core. Verification is milliseconds everywhere.

| Set | q | n | keygen | sign | signature | public key | paper's `|PK|` |
|---|---|---|---|---|---|---|---|
| `d-james-128-q2` | 2 | 189 | 1.5 s | 1.3 s | **24 B** (189 bits) | 1,343,365 B | 1.04 M |
| `james-128-q2` | 2 | 283 | 5.4 s | 5.8 s | 36 B (283 bits) | 1,285,952 B | 2.45 M |
| `d-james-256-q2` | 2 | 390 | 25 s | 13 s | 49 B (390 bits) | 11,174,963 B | 8.82 M |
| `james-256-q2` | 2 | 578 | 32 s | 8 s | 73 B (578 bits) | 10,709,184 B | 10.2 M |
| `d-james-128-q5` | 5 | 94 | 2.0 s | — | 28 B (219 bits) | 315,765 B | 91.4 k |
| `d-james-128-q23` | 23 | 74 | 0.9 s | — | 42 B (335 bits) | 211,788 B | 240 k |
| `toy-d-james-q5` | 5 | 21 | 0.02 s | 0.8 s | 9 B | 3.6 kB | — |
| `toy-d-james-q23` | 23 | 16 | 0.01 s | 9.5 s | 12 B | 2.5 kB | — |

Every signature size matches the paper's `|sig_fast|` column exactly (bar the
`q = 23` rounding noted above), which is a good independent confirmation of the
parameter transcription.

Key generation is fast at every parameter set. **Signing is not, for large
`q`** — and this is the scheme, not the language. The IP modifier costs `q^r`
root-findings per salt (the paper: "the parameter `q^r` must remain small in
practice"), and every set uses `r = 2`, so `q = 23` needs **529** degree-24
root-findings per salt attempt. Over `F_2` that factor is only 4, which is why
the paper's own performance estimates (Table 9) cover the `F_2` sets alone.

Accordingly the shipped vectors are: full signing vectors for every `F_2` set
and every toy set, and key-generation vectors (public-key digests) for all
twenty real sets.

## Layout

```
djames/
  symmetric.py   SHAKE256 XOF, F_q sampling, message hashing
  ff.py          F_q, packed vector backends, K = F_q^n, irreducibility
  poly.py        polynomials over K; root finding (the trapdoor)
  linalg.py      matrices over F_q: sampling, inversion, rank
  params.py      the parameter sets of Tables 3-6, plus toy sets
  codec.py       deterministic byte encodings
  scheme.py      keygen / sign / verify
  kat.py         test-vector generation and checking
  fieldpoly.json cached canonical field polynomials
tools/
  gen_fieldpolys.py   regenerate fieldpoly.json
  gen_kat.py          regenerate kat/*.json
tests/test_djames.py
kat/                  known-answer tests
```

## Testing

`tests/test_djames.py` checks the base fields against their axioms, packed
products against schoolbook, every shipped field polynomial for irreducibility,
root finding against planted roots, matrix inverses, codec round-trips, and —
for all ten toy sets — deterministic keygen and signing, public-key
serialization round-trips, and rejection of tampered signatures, wrong
messages, wrong-length signatures and the all-zero signature.

Known-answer tests pin the public key by SHA3-256 digest and length, and
signatures in full. `kat/toy.json` is re-derived by the default test run;
`DJAMES_FULL_KAT=1` also re-derives `kat/q2.json` and `kat/keygen.json`, which
takes several minutes.

**These are regression vectors, not conformance vectors.** They were generated
by this implementation, so they detect drift in *this* code — they cannot
establish agreement with the paper, and there is no independent implementation
to cross-check against. Conformance rests on the reasoning in [Reading the
paper](#reading-the-paper) plus the central-map test above, and remains
conditional on the two unresolved table ambiguities.
